# Stage 20 — Related Documents / Связанные документы

## Цель этапа

Добавить удобную функцию связывания документов между собой.

Пример пользовательского сценария:

- есть договор;
- к нему загружается приложение;
- позже добавляется дополнительное соглашение;
- затем акт выполненных работ;
- затем счёт;
- все эти документы должны быть связаны между собой в карточке документа.

Главная цель этапа — показать пользователю не отдельный файл, а документный контекст.

## Текущий контекст проекта

Проект уже имеет:

- Organization-aware DMS;
- Document;
- DocumentVersion;
- DocumentActivity;
- AuditEvent;
- UsageEvent;
- DocumentAccess;
- protected document view/download routes;
- import flow;
- AI review flow;
- workflow;
- B2B exchange;
- evidence export;
- security baseline.

Нельзя создавать отдельную систему договоров или отдельную систему связей вне текущего `Document`.

Если в проекте уже есть модель `DocumentRelation`, нужно использовать и улучшать её, а не создавать дублирующую модель без необходимости.

## Что нужно реализовать

Добавить пользовательскую функцию “Связанные документы” в карточке документа.

Пользователь должен иметь возможность:

1. Открыть карточку документа.
2. Увидеть блок “Связанные документы”.
3. Нажать “Добавить связанный документ”.
4. Выбрать другой доступный документ из той же организации.
5. Указать тип связи.
6. Сохранить связь.
7. Увидеть связь в карточке текущего документа.
8. Увидеть обратную связь в карточке связанного документа, если это применимо.

## Типы связей

Минимальный список типов связей:

- приложение к документу;
- основной документ;
- дополнительное соглашение;
- акт;
- счёт;
- заменяет;
- заменён документом;
- скан подписанной версии;
- редакция документа;
- связан по теме;
- другое.

Если в модели уже есть choices для relation type, аккуратно расширить их без поломки существующих данных.

## Правила доступа

Связанные документы должны строго соблюдать права доступа.

Запрещено:

- связывать документы из разных организаций;
- выбирать документ, к которому пользователь не имеет доступа;
- показывать связанный документ пользователю, если у него нет доступа к нему;
- раскрывать название или метаданные недоступного документа через блок связей.

Для выборки документов использовать существующие access helpers, например `get_allowed_documents()` и/или `user_can_access_document()`.

## Аудит и использование

При создании связи нужно записывать `AuditEvent`.

Желательно записывать `UsageEvent`, если текущая архитектура usage tracking поддерживает подходящий event type. Если подходящего типа нет, добавить его аккуратно.

Удаление связи также должно фиксироваться в аудите.

## Evidence export

Связанные документы должны попадать в evidence export как отдельная секция или как часть document metadata.

Важно:

- не включать данные недоступных документов;
- не включать документы другой организации;
- не включать секреты, токены, служебные пути файлов.

## Интерфейс

В карточке документа добавить блок:

“Связанные документы”

В блоке показывать:

- название связанного документа;
- тип связи;
- статус документа;
- дату документа, если есть;
- ссылку на карточку, если пользователь имеет доступ;
- кнопку удаления связи для пользователя с правами.

Форма добавления связи должна быть простой и не ломать существующий интерфейс карточки.

## Тесты

Добавить focused tests:

1. Пользователь может связать два доступных документа внутри одной организации.
2. Нельзя связать документ из другой организации.
3. Нельзя связать документ, к которому нет доступа.
4. Связь отображается в карточке текущего документа.
5. Обратная связь отображается корректно, если предусмотрена.
6. Удаление связи не удаляет сами документы.
7. Создание связи пишет AuditEvent.
8. Evidence export включает связанные документы без утечки чужих данных.

Также прогнать полный набор тестов `dms`.
